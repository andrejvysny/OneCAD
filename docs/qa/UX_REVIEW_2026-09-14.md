# OneCAD UX review — modeling and sketching

**Date:** 2026-09-14
**Passes:** two. Pass 1 explored; pass 2 rebuilt the whole flow from a cold start and re-verified every
finding with a screenshot. See **Second pass** at the end for the verdict ledger, four revised findings
and three new ones.

**Method:** manual real-user session against the real Tauri app (`tauri-agent` MCP, `launch: dev`,
`interaction: foreground`). Every step is physical OS input (`mode: real_user`, `backend: cgevent`)
unless marked otherwise. Session `s-20260914-195854-f4d4`; artifacts and window screenshots under
`.tauri-agent/artifacts/s-20260914-195854-f4d4/`. Action ids below (`A-045`) index that journal.
`session_stop` reported `survivors: []` and ports 1420/4445 free.

**Reference point:** Shapr3D, per the brief. Where a comparison is made it is to Shapr3D's behaviour
in the same situation.

**What was exercised.** New project → sketch on a base plane (Line, numeric entry, auto-constraints,
close the loop) → finish → Extrude (drag handle, typed depth, Add/Cut/New Body) → face selection →
sketch on a face (Rectangle, Circle, Trim, 2D Fillet, delete) → Extrude cut → 3D Fillet → history
feature edit and regen → undo → Measure → command palette → Save (native panel) → snap settings,
viewport orbit/zoom/fit/ortho, tooltips, status hints.

**What was not exercised:** Revolve, Shell, Hole, patterns, Mirror, Move, Datum plane, Combine,
Section view, Variables, Library, export, save-to-disk completion and reopen (the Save As panel was
opened and verified, then cancelled so no file was written to the user's disk).

---

## Verdict in one paragraph

The surface craft is good — status hints, disabled-tool reasons, the trim preview, the feature-edit
preview, the snap-settings panel — and it reads like a product with taste. Underneath it, the two
things a parametric CAD must get right are currently wrong: **the constraint solver reports success
on geometry that violates its own constraints**, and **a sketch drawn on a face does not follow that
face when the parent feature changes, producing a silently wrong model with no warning anywhere**.
The most ordinary sketching actions — draw a rectangle with the Line tool, drag a corner, fillet a
corner, trim a circle — each end in a conflicting sketch, an unusable profile, or silently discarded
dimensions. Grid snapping, which is on by default and advertised by an on-screen badge, does not
snap. Those are the things to fix before any of the polish items below.

## 1. Correctness — blocking

### B1. A sketch on a face does not follow the face; the dependent cut silently does nothing

Steps: extrude a profile 40 mm → select the top face → new sketch on it → rectangle + circle →
extrude-cut → fillet an edge → re-edit the first Extrude from 40 mm to 25 mm.

Result: the body shrinks to 25 mm and the fillet correctly re-binds to the new edge, but **Sketch 2
stays at Z = 40, floating in mid-air above the body** (A-128, screenshot `A-128-after.png`). The
extrude-cut that depends on it now cuts nothing. The pocket disappears from the model. History still
shows `Extrude 10 mm` as a completed feature, and the regen log says the run was clean:

```
regen: published ... steps=5 changed=1 removed=0 failedSteps=0 needsRepair=0   (rev 21)
```

There is no repair banner, no `NeedsRepair`, no diagnostic, no status message. Undoing back to 40 mm
restores the pocket (A-150), which confirms the chain is otherwise intact and that the failure is
specifically the sketch plane not tracking its host face.

This is the exact failure class the project exists to eliminate, and it currently fails silently
rather than deterministically. In Shapr3D a sketch made on a face moves with the face.

**Also wrong regardless of the plane question:** an extrude-cut whose tool volume misses the target
body entirely should not report success. It should fail loudly, or at minimum warn.

### B2. The solver reports a clean sketch while four of its constraints are violated

After removing one redundant constraint from a four-line closed loop, the inspector read
`Under-constrained · DOF 3` with `conflictingIds: []`. A diagnostic read of the same session
(`A-059`, labelled diagnostic) shows the geometry does not satisfy the constraints that are listed as
active and satisfied:

| Constraint | Entity | Actual |
|---|---|---|
| `c1` Horizontal | e1 | ΔY = 1.396 mm |
| `c3` Vertical | e2 | ΔX = 1.047 mm |
| `c5` Horizontal | e3 | ΔY = 1.431 mm |
| `c8` Vertical | e4 | ΔX = 0.953 mm |

The resulting side lengths are 80.000 / 60.000 / 82.000 / 62.825 mm — impossible for a closed loop
whose four sides are all horizontal or vertical. The user sees a rectangle, the inspector says the
sketch is healthy, and the extruded solid is a skewed prism (visible in ortho, `A-146-after.png`).

The likely cause is that deleting a constraint does not trigger a re-solve; the previous, conflicted
positions are kept and the status is recomputed without checking residuals. Whatever the cause, a
"clean" status that does not imply satisfied constraints is worse than no status.

### B3. Drawing a rectangle with the Line tool produces a Conflicting sketch out of the box

Four clicks to close a rectangular loop, accepting every auto-inferred constraint, ends in
`Conflicting · DOF 2 — Conflicting constraints. Remove one to resolve.` (A-045). The auto-inference
applies **Perpendicular in addition to Horizontal/Vertical on the same pairs**, so the set is
redundant. Deleting one Perpendicular cleared the conflict immediately (A-049), and deleting the
second returned the sketch to `Under-constrained` (A-056).

The Rectangle tool, by contrast, produces a clean set — 4 Coincident, 2 Horizontal, 2 Vertical, 2
Distance, no conflict (A-084). So the defect is in the Line tool's inference, not in the solver.

The error message also names no culprit: all eleven constraint rows turn red simultaneously and the
user is told to "remove one" with no indication which.

### B4. A 2D fillet makes the sketch unusable as a profile

Rectangle → circle → trim → 2D fillet on one corner → Finish sketch produces a red status-bar error:

```
Sketch not usable as a profile: opFailed: op failed (OpFailed, recoverable=true): finishSketch:
SketchRegions: incomplete triangulation for region r_698b0a5a3cd6e631
```

(A-098; the same text appears in `dev.jsonl` as `onecad_lib::api` ERROR and as an `fe` `sketch` tag
"finishSketch refused (record committed; regions unavailable)".) Arming Extrude then fails the same
way (A-100). Deleting the fillet arc and re-finishing succeeds with no error (A-106), which isolates
the 2D fillet as the cause.

### B5. Deleting a 2D fillet leaves the profile open

After deleting the fillet arc the two trimmed lines are not extended back to their intersection, so
the loop has a gap and Extrude reports `Regions: 0` (A-107). The user is now stuck between B4 and B5.
Shapr3D and Fusion both restore the corner.

### B6. Dragging a vertex of a closed rectangle fails and corrupts the sketch

A left-drag of a corner from (857, 518) to (900, 560) moved nothing and left the hint "Snap target
not reached; the solver kept the geometry at its solved position", while the sketch flipped from
`Under-constrained · DOF 3` to `Conflicting · DOF 3` with three constraints marked red (A-051). The
conflict persists after release. Direct manipulation of under-constrained geometry is a primary
sketching interaction in Shapr3D; here it neither works nor fails safely.

### B7. Trim silently discards dimensions

Trimming the circle removed both its `Diameter 25 mm` and its `Midpoint` constraint; DOF went 4 → 9
with no warning (A-094). The user's explicit dimension is gone. Shapr3D keeps the radius dimension on
the trimmed arc.

### B8. 2D fillet adds no radius dimension

Filleting a corner at 5 mm added two Coincident constraints and nothing else; DOF went 9 → 14
(A-096). The radius the user typed is not captured, so it cannot be edited later.

## 2. Snapping and sketch feedback

This is where the session was concentrated, per the brief.

### S1. Grid snapping does not snap

Grid snap is ON by default, grid scale 5 mm, snap radius M. Hovering near a grid intersection shows
the `Grid` badge and a readout of `U 46.88 / V −5.07` (A-132); clicking places the point at exactly
those coordinates (A-133). 46.88 is not a multiple of 5, and −5.07 is 0.07 mm off a grid line that is
well inside any plausible snap radius. Earlier in the session the same badge appeared while points
landed at 25.84 / 19.12 on a 20 mm grid.

The badge is therefore advertising a snap that never happens. Either wire it up or stop showing it.

### S2. The snap badge names the wrong snap

Hovering the midpoint of an edge shows `On Curve`. Committing there creates a **Midpoint**
constraint (A-088 → A-091). So the point snapping does work and produces the right constraint — but
the badge never says which snap is engaged. Across the whole session the only label ever seen near
existing geometry was `On Curve`, for edge interiors, midpoints, and near-corners alike.

Shapr3D names the snap it is about to take. That label is the entire contract between the user and
the snapping engine; a generic one is close to useless.

### S3. No endpoint / vertex snap feedback

Approaching an existing endpoint from 4.4 mm (A-043) and then 1.5 mm (A-044) produced no badge, no
highlight on the target endpoint, and no cursor jump. The same at a rectangle corner from 2.8 px
returned `On Curve` and coordinates on the edge but not at the corner (A-087). A user cannot tell
whether they are about to close a loop.

### S4. The snap badge is stale and sticky

The badge renders at the position of an *earlier* step and stays there: it sat at the first line
point while the cursor was 150 px away two segments later (A-033, A-038), survived `Escape` (A-134),
and overlapped a `30 mm` dimension label after a trim (A-094). A constraint-hover label behaved the
same way — a floating `Horizontal` label from an earlier hover was still on screen while a
*Perpendicular* row was being hovered (A-047, A-048).

### S5. No inference guide lines, ever

`Sketch guide lines` and `Sketch guide points` are both ON in snap settings, but no dashed alignment
guide was rendered at any point in the session — not when drawing nearly vertically below an existing
point, not when approaching an endpoint, not when aligning to the origin. Shapr3D's dashed inference
guides are how a user understands *why* a point landed where it did; without them, the snapping is
invisible even when it works (see S2).

### S6. Typed values do not appear until the mouse moves

Typing `30` with the Rectangle tool armed left the chip reading `H 0 mm` and `focus.editable: false`
(A-080). The value had been buffered — moving the mouse one pixel revealed `W 30` already entered
(A-081). A user types, sees nothing, and types again.

### S7. Sketch tools have no live preview of a typed dimension

Typing a length in the Line tool, or W/H in the Rectangle tool, does not update the rubber band
(A-034, A-083) — the preview still follows the cursor until Enter. Extrude (A-065) and 3D Fillet
(A-119) *do* update live and it is much better. Make the sketch tools match.

### S8. `Tab` in the Line tool wipes the typed value

Rectangle and Circle document `Tab` as "second field" (width → height, diameter → radius) and it
works. In the Line tool, which has only a length, `Tab` clears the field instead of being ignored
(A-035). Silent data loss on a key the adjacent tools teach you to press.

### S9. Chips overlap each other and the geometry

The circle's `⌀` and `R` chips overlap each other and the existing `30 mm` dimension label (A-089).
The tool chip in model mode sits directly over the region you are being asked to click (see T1).

### S10. Constraints are anonymous, and conflicts name no culprit

The list is eleven rows reading `Coincident`, `Coincident`, `Horizontal`, `Perpendicular`, … with no
entity names, no numbering, and no way to tell two Coincidents apart (A-046). On a conflict every row
turns red at once (A-045). The rows are `generic`, not buttons, so they cannot be focused or
keyboard-navigated; only hover highlights the geometry.

### S11. Contradictory status vocabulary

After an undo the panel read `Over-constrained · DOF 3 — Sketch is over-constrained` (A-055).
Over-constrained and three remaining degrees of freedom are mutually exclusive to a reader. The three
states (Under-constrained / Over-constrained / Conflicting) also do not map onto a single axis, so
the badge is hard to read at a glance.

### S12. Selecting a sketch entity shows no properties

Clicking an arc selected it and surfaced a two-icon unlabeled context chip, but the inspector did not
change — no radius, no length, no coordinates (A-104).

### S13. Re-opening a sketch arms the Line tool

Double-clicking a sketch in the tree enters it with **Line** active, not Select (A-102). One stray
click adds geometry to a sketch the user only meant to inspect.

### S14. Smaller items

- Constraint list order changes between sessions of the same sketch (A-102 vs A-046).
- `Coincident badges` are OFF by default, so coincidence — the constraint that most often explains
  "why can't I move this" — is invisible.
- Snap-settings naming is abstract where CAD has conventional words: "Sketch guide points" covers
  endpoint/midpoint/centre, while "Quadrant points" and "Intersections" use the conventional names.
- Select mode has no status hint at all; every other tool has a good one (A-050).

## 3. Viewport and camera

### V1. The default camera is a poor first impression

A new project opens in perspective at **FOV 76°** with the camera almost in the ground plane
(A-017). The grid is extremely foreshortened, the horizon sits a fifth of the way down the window,
and a box does not look like a box. Switching the same model to Ortho (A-146) is dramatically more
legible — it is the first screenshot in the session where the geometry reads correctly.

Suggested: open in an isometric-ish three-quarter view; drop the default FOV to ~30–35°; consider
Ortho as the default for a CAD tool. Shapr3D's default camera is a gentle three-quarter with mild
perspective.

### V2. Zoom to fit leaves no margin

`⇧F` fits the body edge-to-edge with the viewport and does not account for the floating toolbar at
the top or the inspector at the right, so the model ends up under the chrome (A-074). Add ~10 %
padding and inset the fit rect by the overlay bounds.

### V3. Entering a sketch on a face zooms in too tight

The projected face fills the viewport corner to corner (A-077), so there is no room to draw outside
it or to see the surrounding body. The opaque teal region fill also hides the 3D context entirely.

### V4. The TOP view of the XY plane is rotated

In a sketch on XY viewed from TOP, screen-right is **+Y** and screen-down is **+X** (A-030). The
conventional top view is X right, Y up. Sketch U/V then does not correspond to X/Y either, which
makes the status-bar readout hard to reason about.

### V5. Coordinate readout does not blank outside the viewport

Moving the cursor over the sidebar leaves the status bar showing stale, implausible values
(`X 1022.96 Y 3318.15`, A-121).

**Orbit / pan / zoom themselves are fine.** Shift + right-drag orbits at roughly 0.55°/px, which is
in the normal range; wheel zoom classified correctly as a mouse; Home and Fit work. The navigation
help popover is accurate and well written.

## 4. Tool chips and operations

### T1. The tool chip covers the geometry it asks you to click

With Extrude armed the chip floats directly over the sketch region, and a click meant for the region
landed on the chip and was **silently swallowed** — the count stayed `0 regions` and nothing
indicated the click had been absorbed (A-108). Clicking a few pixels to the left worked immediately
(A-109). The chip has a `Dock` affordance, which suggests this is known, but the default position is
wrong and the swallowed click needs feedback.

### T2. The unlabeled `↔` in the Extrude panel is "Symmetric", and reads as "flip direction"

Clicking it while setting up a cut produced a downward-looking preview and a committed feature with
`Symmetric: Yes` (A-115, A-116) — a symmetric ±10 mm cut rather than the 10 mm downward cut intended.
An unlabeled double-arrow next to a direction-dependent operation will be read as a flip by everyone.
Label it, and add an actual direction flip (T3) — currently the only way to reverse an extrude is to
drag the handle the other way.

### T4. The Cut preview turns the entire body bright red

(A-112.) Red-on-everything reads as an error state, not as "this will subtract". Shapr3D tints only
the tool volume. Consider tinting the removed volume and leaving the target body neutral.

### T5. `Direction: Normal [0, 0, 1]` never updates

It still read `[0, 0, 1]` after the symmetric toggle changed the preview (A-115) and after commit.

### T6. Re-editing an Extrude hides half its options

In feature-edit mode the panel shows only the draft-angle field; `Blind / Through all / To next / To
face` and `New Body / Add / Cut` are gone (A-123). You cannot change an extrude from Add to Cut
after the fact.

### T7. Inconsistent rounding between the drag handle and sketch dimensions

Dragging the extrude depth handle produced `52.09 mm` with no snapping to round values (A-062), while
sketch dimension rounding is ON by default. Pick one policy.

### Good, for the record

- The trim hover preview — target segment red, the rest cyan — is excellent and exactly right
  (A-093).
- The feature-edit preview (solid below the new height, ghosted above) plus the honest hint
  "Approximate feature-edit preview; final geometry updates on Apply" is very good (A-126).
- Auto-projecting the host face's edges into a new face sketch, with lock badges, is a good touch
  (A-077).
- Disabled tools explain themselves: "Select a sketch region (or a sketch) to extrude" (A-006).
- Per-tool status hints are genuinely useful throughout.
- The snap-settings panel is unusually rich for a young app.
- Editable sketch dimensions directly in the inspector (A-122).

## 7. Suggested priority

**Fix before anything else**

1. B1 — sketch-on-face must follow its host face, and a cut that removes nothing must not report
   success. This is the project's stated reason for existing.
2. B2 — never report a clean status on geometry that violates its constraints. Re-solve after a
   constraint is deleted, and gate the status on residuals.
3. B3 — stop the Line tool emitting Perpendicular alongside Horizontal/Vertical.
4. B4 / B5 — 2D fillet must produce a triangulable region, and deleting one must restore the corner.
5. S1 — make grid snapping snap, or remove the badge.

**Next — the sketching feel, which is what a Shapr3D comparison is really about**

6. S2 + S5 — name the snap in the badge (`End`, `Mid`, `Centre`, `On curve`, `Grid`, `Intersection`)
   and draw the dashed inference guide that explains it. These two together are most of the
   perceived quality gap.
7. S3 — endpoint/vertex snap needs a highlight on the target and priority over on-curve.
8. S4 — clear the snap badge when the snap ends; anchor it to the cursor.
9. B6 — dragging under-constrained geometry must work, and must never leave a conflict behind.
10. B7 / B8 — trim must preserve dimensions; 2D fillet must create a radius dimension.
11. S6 / S7 / S8 — typed dimensions should render immediately, preview live, and `Tab` must never
    destroy input.

**Then — clarity**

12. S10 / S11 — name constraints by their entities, point at the actual conflict, and use one status
    vocabulary.
13. N1 / N2 — a user-facing error layer; never show enum names, flags or region hashes, and never
    let an error reflow the status bar.
14. T1 / T2 / T4 — move the tool chip off the pick target (and give feedback when it eats a click),
    label the Symmetric toggle and add a real direction flip, and stop painting the whole body red
    on a cut.
15. V1 / V2 / V3 — a sane default camera, a fit that respects the chrome, and breathing room when
    entering a face sketch.
16. N3–N11, C1–C11 — naming and chrome consistency.

# Second pass — verification (same day, new session)

The whole flow was rebuilt from a new project in a second cold-start session, foreground, physical
input. A native window screenshot was captured at the moment each finding occurred. Raw captures are
under `.tauri-agent/artifacts/s-20260914-195854-f4d4/`; the published report embeds one per finding.

## Ledger

- **52 of 56** pass-1 findings were re-run. **All 52 reproduced.** None failed to reproduce.
- **4** could not be re-reached — N3, N4, N8 (fillet-panel naming) and N10 — because the new finding
  **T8** makes an edge selection practically impossible in the second session's camera setup. They
  stand on pass-1 evidence and are labelled as such in the report.
- **4** were revised in detail: S3, V2, T2, T3 (below).
- **3** new findings: S15, T8, N12 (below).
- **2** loose pass-1 impressions were dropped rather than promoted: "orbit also changes the camera
  distance" did not reproduce (orbit ran at ~0.55°/px with no distance change), and "the viewport has
  no hover pre-highlight" is wrong — faces do highlight on hover; only edges do not, which is T8.

## Revisions

**S3 — revised.** Pass 1 said there was no endpoint snap. Too strong: a click 2.2 mm from the open
endpoint *does* close the loop and create the Coincident (A-182 shows the region filled). What is
missing is all the feedback around it — no badge, no highlight on the target endpoint, and a readout
showing raw unsnapped coordinates right up to the click (A-181). Restated as: *closing a loop happens
silently*. Given B5 (an open profile costs a whole extrude), that is the wrong thing to leave invisible.

**V2 — revised.** Pass 1 said Zoom to fit lands edge-to-edge under the chrome. Measured in pass 2, the
real behaviour is an off-centre fit: after `⇧F` the body sat 63 px from the left viewport edge and
267 px from the right, and low in the frame (A-201). Most likely the fit box includes the origin triad
and datum markers rather than only the visible bodies. Both halves need fixing: fit to visible
geometry, and inset the fit rect by the floating toolbar and inspector.

**T2 — revised.** The Symmetric control is *not* unlabelled in the markup — `ui_inspect` (A-194)
reports `aria-label="Symmetric"` and `title="Symmetric (hold Alt while dragging)"`. But neither
reaches a sighted user: no visible label, and a deliberate 3-second hover produced no tooltip at all
(A-195). The app's own instant tooltip system, used on the main toolbar, is not wired to this control
and the native `title` tooltip does not render in this WebView. The finding stands; the fix is a
visible label plus the app's tooltip system, not an `aria-label`.

**T3 — revised.** There *is* a way to reverse an extrude: drag the depth handle back through zero and
the value goes negative (`−16.3 mm`, A-248), which correctly reverses the cut. Nothing tells you that,
the arrow does not flip to a positive value, and there is no button — so the discoverable-looking
control (T2) is the wrong one and the working one is undocumented.

## New findings

**S15 — live dimension chips mix precisions in the same pair.** While drawing a rectangle the two
chips read `W 30 mm` and `H 16.225 mm` at the same moment (A-207) — one integer, one to three
decimals, while every other chip in the app rounds to whole millimetres.

**T8 — edges cannot be picked, so Fillet / Chamfer is unreachable. BLOCKING.** Five clicks aimed at
three different silhouette edges at 1–3 px accuracy all selected the adjoining *face* instead
(A-266, A-267, A-273, A-287). Hovering an edge produces no pre-highlight at all (A-271), while
hovering a face does highlight it (A-268) — so there is no feedback to aim with. There is no
alternative entry point: `Fillet / Chamfer` is disabled with a face selected (A-265) **and** with a
whole body selected (A-289); `Shell` is likewise disabled with a body selected. Pass 1 did select an
edge on the first attempt at a different camera angle, so this is inconsistent rather than impossible.

**N12 — the history row drops the sign of a negative feature value.** A feature whose inspector value
is `−15 mm` is listed in the history row as `15 mm` (A-255). The sign is what makes it a downward cut.

## Strengthened evidence

- **S1** — settled with an adjacent-pixel probe: moving 2 px changed the readout from `U −46.00` to
  `U −44.97`, i.e. continuous 0.515 mm/px motion with no step and no lock, while the `Grid` badge was
