01

Executive summary

OneCAD gains an abstract Generator operation: a single typed KnownOperation variant whose parameters are a discriminated union of recipes. A recipe is a fully parametric solid generator — no sketch required — that takes a placement reference (a planar face or datum plane, plus a frozen center point) and a typed parameter block, and mints a new body (body_<opId>, decision D1). The first recipe family is gears, achieving functional parity with the twelve gear types of the FreeCAD freecad.gears workbench: involute external, involute rack, internal involute, cycloid, cycloid rack, hypocycloid cam, spherical-involute bevel, crown, ZA worm, GT/HTD timing, T-profile timing, and lantern.

The design is deliberately unoriginal where OneCAD already has a proven pattern. The Generator is a Hole that mints instead of cuts: Hole's conditional-parameter contract, four-boundary validation, frozen-point placement fencing, exact-preview-for-free via PreviewOp, and bespoke chip-cluster UI are copied wholesale. What is genuinely new is geometry infrastructure — the worker today has no B-spline construction, no helix, no sweep or loft, and no 2D fillet wrapper. Those are built once, in the kernel's geometry layer, and serve every future generator (springs, cams, threads) as well as any future loft/sweep work.

What ships first (G0–G1)A pure-C++ gear math core cross-validated against the reference implementation, plus the Generator op plumbed end-to-end with the involute spur recipe: schema, Rust, worker, exact preview, history node, chip UI, and a full analytic oracle test suite.
What is structurally excludedNo addon-extensible generators (ADR-0002 — recipes are typed enum variants). No arbitrary-execution hatch. No 2D-wire output mode. No assembly kinematics in v1 (a mating helper is a G5 option). Gear tooth sub-geometry is not ElementRef-referenceable.
Biggest technical riskHelical sweep infrastructure (PipeShell Frenet + solid sewing) — the exact point where the reference addon is fragile and under-tested. Isolated into phase G2 so extrude-only recipes ship independently.
Validation postureTierA publication (full audit_shape evidence including self-interference) from day one — making gears the second operation after fillet with deep validation, advancing the project's uniform-validation goal rather than adding to its asymmetry.
Strategic noteGenerated parametric parts are where a local-first, correctness-first CAD can be strictly better than the incumbent ecosystem: the gear's parameters live in the same typed operation contract the UI and any future agent client share, its failures surface as graded refusals (NeedsRepair / OP_FAILED), and its geometry is oracle-tested against closed-form mathematics — none of which is true of the reference implementation this spec ports.
02

Reference analysis — freecad.gears

2.1 Structure

The addon (v1.3.0, GPL-3.0) separates cleanly into a pure-math layer (pygears/: numpy-based, FreeCAD-independent) and a FreeCAD feature layer (freecad/gears/: 12 feature classes + kinematic connectors + workbench chrome). The feature layer converts sampled point arrays into B-reps through FreeCAD's Part module — a thin Python wrapper over OCCT — which means every construction call maps 1:1 onto an OCCT C++ API. freecad/part.py is an import shim, and pygears/transformation.py (symbolic matrices via sympy) is dead code at runtime.

2.4 Upstream fragilities — explicitly not ported

  • Unsewn helical solids. Upstream's helical_extrusion carries a compound-extraction hack ("why the heck is makeShell from this empty after mirroring?") with sewShape() commented out; the single unit test for it is xfail. OneCAD sews and validates (BRepCheck_Analyzer + TierA audit) or refuses.
  • Index-based fillet insertion. Fillets are inserted at hard-coded edge positions with a pop-and-retry fallback. OneCAD identifies fillet sites geometrically (position/tangent), which is robust to sampler point-count changes.
  • Bevel overflow warn-and-continue. Height ≥ cone distance prints a warning then produces garbage. OneCAD refuses with OP_FAILED and a diagnostic — the project's fail-closed rule applied to generated geometry.
  • Ruled-loft bevel approximation. The mid-face between inner/outer spherical involutes is interpolated, not the true surface; spiral bevel is a radius-proportional twist, not Gleason geometry. The math is ported as-is (parity goal), but the schema and UI copy state the approximation honestly.
  • Rack simplified mode. A constant-topology fake (middle teeth bridged) that exists only to dodge FreeCAD's topological naming problem. Unnecessary in OneCAD — see §7.
  • transformGeometry per-tooth replication. Re-parameterizing copies invite tolerance creep; OneCAD uses location transforms (TopLoc_Location) for exact per-tooth copies.
  • height = 0 2D-wire mode. OneCAD has a real sketch system; a 2D gear profile is a possible future sketch generator, not a gear op mode.
  • Connector kinematics. Gear-pair placement/phasing is assembly math, not geometry generation. Deferred to the G5 mating-helper option.
Testing debt upstreamThe reference has exactly one unit test (marked xfail) plus screenshot SSIM regression. There are no volume checks, no analytic curve checks, no diameter checks. There is no upstream ground truth to port. The oracle suite in §10 is therefore a build item of this project, not a nice-to-have — the Python cross-check harness (C++ sampler output vs reference output over a parameter sweep) is the only practical equivalence evidence available.

OneCAD architecture integration

3.1 The Hole precedent — copied, not reinvented

Hole (WP-C T3) is the newest operation and the closest analog to a generated feature: fully parametric (no sketch), typed conditional parameter blocks, face-pick placement with a frozen world point re-projected onto the resolved face each regen (fenced at 1e-3 mm), exact preview, and one history node regardless of profile subtype. The Generator inherits every one of these patterns:

04

Framework design — the Generator operation

4.1 One operation, not twelve

A single Generator op with a recipe union wins over twelve per-type ops on schema surface (one §7.3 family), UI (one tool, one chip cluster with a recipe picker — exactly how Hole collapses simple/counterbore/countersink into one feature), history (one node kind, re-editable across recipe changes while keeping record identity), and preview (one lane). The cost — a discriminated union where only the active recipe's block is non-null — is already paid: Hole's conditional-block contract is the proven pattern, enforced at all four trust boundaries.

4.2 Wire payload shape

{ "opType": "Generator", "opId": "op_…", "stepIndex": n, "inputs": [ ], "params": { "recipe": "involuteExternal", "placement": { "face": , // null ⇒ datum/explicit frame "frame": , // origin + Z-up axis, frozen at authoring "point": [x, y, z] // world-space center, frozen, re-projected per regen }, "involuteExternal": { …block… }, "involuteRack": null, // every inactive recipe spelled null "internalInvolute": null, … // one key per recipe family }, "determinism": { "parallel": …, "occtOptions": … } }

Dimensional parameters ride the existing scalar convention (number | {value, expr?}, §7.3 header). Units are millimetres and degrees, matching every existing op; fillet radii keep upstream's convention of multiples of module where the standard literature does, and are absolute where it doesn't (timing-T) — the schema table in §5 marks which is which.

4.3 Shared seams every recipe inherits

  • Placement. Face pick (Hole semantics: re-project frozen point onto resolved face, inward normal = gear axis) or an explicit frozen frame for datum/world placement. Placement refs are the op's only derive_inputs contribution.
  • Minting. ctx.bodies.create("body_" + op_id, op_id, shape) + created body event + empty delta. Compound recipes (hypocycloid cam with pins) mint ordinal children body_<opId>:<k> under the ranked-solids rule — no free-form compounds in the document.
  • Publication. publication_decision with per-recipe PublicationPolicy (§8). Empty, invalid, or self-intersecting results are refused with GEOMETRY_INVALID/OP_FAILED — never published, never warn-and-continue.
  • Preview. Exact, via the shared candidate executor; the chip edits params against a live ghost at the existing throttle floor.
  • History. One named node per generator instance: Gear — Involute 20T m2-style display naming from recipe + headline params; full param re-edit via updateOperationParams.
  • Determinism. Samplers are pure functions of params (no wall-clock, no hash-order iteration); construction honors ctx.parallel/ctx.occtOptions; the kernelbench double-run discipline applies from G1.

4.4 What the abstraction buys later

The second recipe family (e.g. compression/extension springs — helix + sweep, already paid for in G2) drops into the same schema section, the same FSM shape, the same chip cluster shell, and the same publication path without touching placement, minting, preview, or history code. That is the test the abstraction must pass; until a second family exists, no general registry ships.

6.2 New kernel geometry layer

New files under worker/src/kernel/geometry/ (beside the existing EdgeChainer):

  • BSpline.{h,cpp} — interpolate-through-points wrapper with explicit degree/tolerance policy and failure mapping (non-convergence ⇒ graded refusal, not empty curve).

07

Topological naming & generated geometry

A gear's faces and edges are entirely generated — their count and identity change with the tooth count. Binding a downstream ElementRef to "tooth N's flank" across a parameter edit is exactly the silent-wrong-bind scenario OneCAD's ladder exists to prevent. The policy:

  • Only the generated body's root id, its placement inputs, and (when present) the bore axis/cylindrical faces carry referenceable identity. Bore faces are stable sub-features (present iff the corresponding hole param is on) and may mint refs — this is what makes a gear shaft-hole usable by downstream Hole/Extrude-on-face flows.
  • Tooth flanks, tips, roots, fillets are not referenceable. Picking them for a downstream op yields a truthful UI refusal ("generated tooth geometry is not stable across parameter edits"), not a bind that breaks later. The schema states this normatively; the picking layer enforces it by filtering body sub-shape kinds.
  • Parameter edits that change topology are ordinary param edits (record identity preserved, like Hole profile flips). Downstream refs bound to the placement face or bore survive; refs bound to anything else on the gear were never allowed to exist.
  • The generator's own empty element-map delta (NewBody, nothing pre-existing tracked) keeps apply_history out of the loop entirely for these ops.
ConsistencyThis is the project's core value proposition — deterministic NeedsRepair over silent wrong binds — applied one level down: it is better to declare tooth geometry unreferenceable than to let a descriptor bind to a plausible-but-wrong flank after a tooth-count edit.
08

Validation & publication policy

  • Input side: placement refs go through the standard preflight (operation_ref_ownership_repairs); there is no host body to validate — generators are upstream-free beyond placement.
  • Parameter side: four-boundary validation (FSM → wire mapper → edit/session.rs → worker). The worker's re-validation is unconditional and includes geometric feasibility: teeth ranges, fillet ≤ space available, bevel height < cone distance, undercut ⇒ rootFillet = 0, helical handedness consistency. Every refusal is a bounded {severity, code, message, stage, evidence} diagnostic — never a silent fallback.
  • Publication side: single-solid recipes ⇒ single_solid_policy("Generator", TierA) — full audit_shape evidence (null shape, BRepCheck_Analyzer, exactly-one-solid, finite positive volume, tolerance ceiling, self-interference via BRepAlgoAPI_Check). The hypocycloid-cam family mints ordinal child bodies, each audited under the same TierA policy. This makes Generator the second operation family after fillet with deep post-op validation — a deliberate contribution to the project's uniform-validation goal, not an exception from it.
  • Failure semantics: impossible geometry ⇒ recoverable OP_FAILED / GEOMETRY_INVALID with actionable message (which param, which constraint, suggested range); stale placement ⇒ NeedsRepair; preview failures block commit structurally (SCHEMA §7.6 rule).
09

User experience

9.1 Flow

  1. Entry — toolbar (Model flyout) or keybinding; FSM enters facePick: "Click a flat face to place the gear, or press Enter for the XY datum."
  2. Placement — face click freezes the center point (Hole semantics); Enter uses the default datum frame. Axis = gear rotation axis, displayed as a temporary glyph.
  3. Armed — exact preview ghost appears immediately with default recipe (involute external, sensible defaults); chip cluster opens.
  4. Recipe & params — recipe picker (segmented or dropdown) at chip top; parameter sections below; every keystroke re-previews (200 ms trailing floor); computed read-outs (da/df/dw/lead angle) update live; invalid combinations disable fields with inline explanation (e.g. root fillet under undercut) rather than silently zeroing.
  5. Commit — ✓/Enter; blocked while the preview reports a structural failure. History node appears as Gear — Involute 20T m2.
  6. Re-edit — L1 params replace via the FSM seed (Hole pattern).

9.2 Chip cluster

Bespoke GeneratorChipCluster.tsx (no generic form renderer exists — matching the per-op chip convention): recipe picker; grouped parameter sections (Base / Tooth / Helix / Fillets / Holes / Accuracy) reusing the shared chip primitives (SegmentToggle, CountStepper, DimensionInput); computed-values strip; a presets popover (preferred module series, standard pressure angles, the timing-belt profile table). All colors from tokens.css; no raw hex; theme-safe by construction.

9.3 Honest-geometry copy

Where a recipe is an approximation (bevel mid-face ruled loft; spiral bevel not Gleason; pressure-angle clamping on the cam), the chip says so in one plain sentence behind an info affordance. This matches the project's policy of surfacing limitations in-product rather than in footnotes.

9.4 Explicitly out

No 2D-wire mode; no rack simplified-topology switch; no connector/kinematic placement in v1 (G5 option: a mating helper that computes center distance for a selected gear pair — including the shifted-pair Newton solve — and applies tooth-phasing offset, as a placement-time assist rather than an operation); no loft/sweep generalization of the gear paths.

Testing & oracle strategy

10.1 The oracle problem

The reference implementation has no numeric oracles. OneCAD's suite is therefore built from three independent legs, each sufficient to catch a different failure class:

  1. Closed-form analytic oracles — da/df/dw/dg, transverse pitch, lead angle, arc-table radii: pure arithmetic, per recipe, table-driven.
  2. Cross-check harness — a local Python script runs the reference addon and the C++ samplers over a parameter sweep (teeth × module × α × β × shift × undercut × fillets, plus per-recipe edge cases) and diffs sampled profile points within tolerance. This is equivalence evidence against a shipping implementation. Runs locally only — GPL reference code is never wired into OneCAD CI (license hygiene and determinism).
  3. Kernel oracles — per-recipe gtest: BRepCheck validity, exact-one-solid, analytic volume bounds (bounding estimates with generous tolerance for splined profiles; exact for arc/line profiles like timing), curve-deviation checks (sampled BSpline points vs analytic curve ≤ 1e-6-quantized tolerance), determinism double-run byte-identity.

Open questions (non-blocking)

  • Internal-gear naming: internal-native param names (internalClearance/internalHead) with sampler-side swap — recommended — vs literal upstream naming for parity readers.
  • Referenceable bore faces: mint refs for bore cylinders (enables downstream shaft features) vs nothing referenceable at all in v1. Recommendation: bore faces yes, teeth never.
  • Mating helper (G5): wanted at all, and if so, placement-assist vs a true assembly-kinematics feature later.
  • Timing-T fillet convention: keep upstream's absolute radii (documented exception) or normalize to ×m for cross-recipe consistency (deviates from upstream).
  • Second generator family: springs (helix + sweep, nearly free after G2) vs threads vs cams — the choice that will retroactively validate the framework abstraction.
