The Component Library

Reusable mechanical components — screws, bearings, motors, and anything a user authors — placeable in one gesture, parametric where it matters, and honest about what happens when a definition is missing. Grounded in OneCAD's actual architecture and in what Fusion, SolidWorks, Onshape, and FreeCAD each got right and wrong.

01

Why this, and why now

OneCAD is at v0.1.0 with near-zero traction. The gap between a CAD tool and a CAD workflow is content: nobody wants to model an M8 socket-head screw, a 608 bearing, or a NEMA 17 stepper from scratch, and nobody wants to hunt one down on a website, download a STEP, import it, and then move-align-joint it into place. That friction is why every mainstream CAD ships or integrates a parts library — and why Shapr3D and Plasticity users file the same feature request year after year.

The timing is architectural, not just commercial. The platform refactor just landed, and a component library is the first feature that exercises every piece of it at once:

  • ADR-0002's ModelingService facade — the library must live behind it, proving the boundary is real.
  • ADR-0003's controlled UI slots — the library panel is a slot contribution, not raw DOM.
  • The sha256 content-addressed import-blob machinery already in onecad-core/src/io/imports.rs — a library store is the same idea at a larger scale.
  • The background-tasks chip — which today has no producer. Library indexing and import are its first honest job.
  • The start screen's ProjectCard anatomy — templates slot directly into it.
The core claim

A component library is not a content pack. It is the feature that turns OneCAD's topological-naming correctness spine from an internal virtue into a user-visible one: a placed library part that can never silently change shape is something SolidWorks Toolbox has failed to guarantee for twenty years. That is the pitch.

02

What the field teaches

Four archetypes dominate, and they split along exactly one axis: closed-but-polished vs. open-but-janky.

SystemParametric?Insert-time alignmentLinkageSignature failure
Fusion 360 + McMasterNo — dumb solid per part numberNone; drops in space, joint laterNone — one-shot importThird-party CDN bug once served the wrong part for every insert
SolidWorks ToolboxYes — configurationsBest-in-class mate references, Smart FastenersFile reference to shared folderMissing config → fastener silently reverts to largest size on another machine
Onshape Standard ContentYes — configs + Auto-SizeStrongest: mate-connector snap, flip key, bulk/stack insertLive linked, versionedClosed — users can't add their own parts with the same UX
FreeCAD FastenersYes — table-driven generatorsAttach to circular edge, auto-size from radiusLive object, but file won't load without the WBPortability: recipient must install the workbench or you bake to dumb solids
Shapr3D / PlasticityNo library at all — Plasticity doesn't even have instances. The most-upvoted requests.

Patterns worth stealing outright

Auto-Size (Onshape)

Click a hole's circular edge → the library picks the nearest smaller bolt (rounds down for holes, up for shafts/nuts). Nobody wants to read a size table. FreeCAD does the same from edge radius.

Mate-at-insert (Onshape / SolidWorks)

Concentric + coincident created by the insert gesture itself, not as a follow-up command. Fusion's "drop in space, joint later" is the explicitly hated counter-example.

Config via small dropdown set

Size, length, thread detail — a handful of constrained choices in the insert dialog. Orientation flip on a single key (Onshape's A, SolidWorks' Tab).

Bulk & stack insertion

Pre-select a planar face → fasten every hole on it in one gesture. Stack a washer + nut under an already-placed bolt. The common case is "populate N holes," and the tool should know it.

Failure modes to design against

The cardinal sin — silent geometry substitution

SolidWorks reverting a placed fastener to its largest size when a configuration is missing is the single most destructive failure in the field. OneCAD's answer must be structural: placed geometry is always cached locally, and a missing or changed definition surfaces NeedsRepair — never a silent swap. This is not a new idea for OneCAD; it is the project's founding invariant applied to a new surface.

  • Network fragility. Fusion's wrong-part CDN bug and Toolbox's VPN stalls both come from making the library a live external dependency. OneCAD's library is local-first and must work fully offline.
  • All-or-nothing libraries. Every system forces "closed but polished" (Onshape) or "open but janky" (FreeCAD). The clearest market gap — requested explicitly by Onshape, Shapr3D, and Plasticity users — is first-class user libraries with the same insert UX as built-in content.
  • Timeline pollution. Fusion's capture-position clutter shows insertion must be a single atomic, undoable operation that drops only what the user picked.
03

The component model

The direction is locked: static and parametric from day one. The design consequence is the most important sentence in this document — a static STEP solid and a parametric native definition are two kinds of the same Component concept. They share identity, metadata, parameters, attachments, and placement. They differ only in how geometry is produced.

Anatomy of a Component

// component.toml — the manifest at the heart of every package
[identity]
id        = "onecad.std.iso4762"      // stable, namespaced, never reused
version   = "1.0.0"                  // semver; drives opt-in upgrade
revision  = "sha256:9f2c…"           // content hash of the whole package

[metadata]
name        = "Socket Head Cap Screw"
standard    = "ISO 4762"
designation = "ISO 4762 M{d}x{l}"     // BOM-ready string template
category    = ["fasteners", "socket-head"]
tags        = ["metric", "shcs", "cap-screw"]

[source]  // exactly one of three kinds — see below
kind = "generator"                  // embedded | generator | document

[parameters]  // the parametric signature — what a placed copy can vary
thread = { role = "free", key = "M6", domain = ["M3","M4","M5","M6","M8"] }
length = { role = "free", value = 20, snap = "preferred" }   // ISO 888 series
head_d = { role = "table", from = "iso4762.dk" }            // derived, locked
thread_detail = { role = "free", value = "cosmetic" }       // see §07

[attachments]  // mate points — the platform feature, see §05
head_seat = { on = "face:head_underside", frame = "auto", accepts = ["plane"] }
shank_axis = { on = "cylinder:shank",    frame = "auto", accepts = ["cylinder", "hole"] }

The three source kinds

Embedded

static

A self-contained STEP/BREP blob, content-addressed by sha256 — the exact pattern already in imports.rs. Geometry is produced by reading the blob. This is how imported vendor parts and most user-dropped-in files work.

Generator

parametric

A built-in, versioned recipe keyed by standard id (iso4762, bearing.6200, nema.17). Geometry is produced by running the generator through the existing worker op path with the instance's parameter values.

Document

user-authored

A reference to a frozen .onecad document. Geometry is produced by replaying that document's history with the instance's parameter overrides. This is how "Save as Component" works — see §08.

Why one concept, not two features

If "static import" and "parametric standard part" were separate features, the UI would fork, placement would differ, and a user couldn't promote an imported STEP into a parametric family later. Unifying them means the panel, the search, the drag-to-place gesture, the mate snapping, and the instance machinery are built once and serve all three source kinds. The source.kind field is the only place the difference exists.

Attachments — the part that makes it a platform

A downloaded STEP file is dumb because it carries no placement intent. A OneCAD component declares attachments: named mate points, each with a local frame and a list of geometry types it accepts. This is the data that powers Onshape-style mate-snap, and it is what permanently separates a library part from a file on a website.

Critically, attachments are authored once by the library author (or inferred automatically for generator kinds — a screw's shank axis and head seat are known by construction) and consumed by every placement. The user placing the part never thinks about them; the part just snaps.

04

The placement decision — resolved

This was the question left to the brainstorm: do placed components become ordinary document bodies (copy-in, like today's STEP import), or do they stay first-class, identifiable, editable things?

Copy bodies in
like today's ImportStep
  • Simple. No new KnownOperation, no identity machinery, reuses the existing import path.
  • Zero dependency. The document is fully self-contained the moment the bodies land.
  • But: the part forgets what it is. No "change M6×20 → M8×30." No "replace all 8 screws with the flanged variant." No BOM identity. No answer when the library updates. It is Fusion's McMaster flow — the one users call "tedious" and "polluting."
vs
First-class Instance
a new Component op + cached geometry
  • Identity survives. The placed thing knows it is "ISO 4762 M6×20, instance #4." Parameters stay editable; replace-in-place is possible.
  • Correctness-aligned. A missing/changed definition surfaces NeedsRepair — never SolidWorks' silent swap.
  • Self-contained anyway. Placed geometry is cached locally, so a document opens with zero library dependency. Linkage is a convenience, not a requirement.
Decision: first-class Instance, geometry always cached. The deciding argument is OneCAD's own founding invariant — deterministic NeedsRepair beats a silent wrong bind. That principle doesn't stop at sketch references; it is exactly the guarantee a parts library needs to avoid the field's worst failure. Copy-in is what you do when you don't trust your identity machinery. OneCAD built the machinery precisely so it never has to do copy-in.

What this means concretely

Under ADR-0002, a new KnownOperation variant is a built-in change, not an addon — which is correct here; the library is core product, not an extension. The recommended operation family (each a single atomic, undoable op, in keeping with the history-publication rules from the UX audit):

OperationPurposeNotes
PlaceComponentInstantiate a library component into the documentCarries component id + version + revision, parameter values, an optional target attachment, and a TransformBody-style frozen-pivot placement. Publishes the cached geometry as its result.
SetComponentParamsEdit a placed instance's parametersM6×20 → M8×30. Re-runs the generator / re-reads the resolved variant, re-publishes geometry, keeps identity and mates where still valid.
ReplaceComponentSwap an instance to a different component"All M6 SHCS → flanged button head." Mates re-resolve through the naming ladder; failures become NeedsRepair.
DetachComponentDrop identity, keep geometry as ordinary bodiesThe honest "break link" escape hatch — explicit, never silent. Result is exactly what copy-in would have produced, on demand.
Mates are a separate op tier

Instance placement does not require a full assembly-mate system to ship. PlaceComponent with a target attachment + frozen pivot stands on its own. Persistent, solving mates (concentricity that keeps working after the target moves) are a later, separable layer — see §05 and the phasing in §11. Do not let the mate system block the library.

05

Mates & snapping — the placement UX

The target is full mate-like placement: click a cylindrical face and a screw snaps concentric; click a planar face and it seats flush. The encouraging finding from the repo is that OneCAD already owns most of the machinery.

The reuse opportunity

OneCAD's ElementRef / AnchorIntent already carries a localFrame (origin + x/y/z basis) and surface_uv captured at selection time, and the resolution ladder already re-finds faces after upstream edits. A mate is, structurally, a pair of ElementRefs plus a transform constraint — which means mate snapping builds on the naming spine instead of inventing a parallel picking system.

Attachment inference rules

Placement snaps by geometry type, not by the user naming anything. When the user hovers geometry during a drag-place, the solver classifies the target and matches it against the dragged component's attachments:

Hovered targetComponent attachment it satisfiesResulting snap
Cylindrical face / hole boreshank_axis (accepts cylinder/hole)Concentric — component axis aligned to the cylinder axis, seated at the near end
Planar facehead_seat (accepts plane)Flush / coincident — mating face coplanar, normal-aligned, at the pick point
Circular edge (hole rim)both — axis + seatConcentric + coincident in one click; the preferred fastener gesture
Hole feature (from Hole op)shank_axis + auto-sizeSnap concentric and set the size parameter to the nearest smaller standard size

The gesture, end to end

  1. Drag from the panel (or double-click). A live ghost of the component follows the cursor — uncommitted geometry, consistent with the modeling contract's "live result" state.
  2. Hover a target. The solver classifies it, finds the matching attachment, and previews the snap: axis line for concentric, a seating plane flash for flush, both for a hole rim.
  3. Auto-size on holes. Hovering a hole offers the nearest smaller standard size; the size chip updates live. (Onshape Auto-Size, FreeCAD edge-radius sizing.)
  4. Flip with a key — A flips orientation along the mate axis, Tab cycles alternative valid attachments when more than one matches.
  5. Click to commit. One atomic PlaceComponent lands: identity, parameters, frozen placement, cached geometry, and (if a target was snapped) the recorded attachment pair.
  6. Or drop in free space and position later with the Move tool — the fallback, never the required path.
Honest constraint — picking & face classification

The snap solver needs reliable surface classification (plane / cylinder / circular edge) on hover. OneCAD's ladder computes descriptors offline for refs; the interactive solver needs a fast, read-only variant of that classification on the render thread's pick result. This is real new work and the main technical risk in the placement UX — it is flagged as its own phase-0 spike in §11 rather than assumed away.

Persistent mates — later, separable

Snapping-at-insert is a solved problem with the machinery above. A persistent mate — where moving the target plate re-seats every screw in it — is a constraint solver over the attachment graph, and it is genuinely a v2 concern. The design keeps the door open: because PlaceComponent already records the attachment pair as ElementRefs, a future mate system reads them as constraints without re-authoring any placed part. Nothing done in v1 is thrown away.

06

Storage — local now, registry-ready

The direction: a local library that works fully offline, but with a package and identity format designed so a future curated community registry is additive, not a redesign.

The on-disk shape

~/OneCAD/library/
├── library.json                 # the index — IS the future registry manifest
├── onecad.std.iso4762/          # one directory per component package
│   ├── component.toml           # the manifest from §03
│   ├── tables/iso4762.json      # dimension data (generator kinds)
│   └── preview.webp             # thumbnail for the panel
├── onecad.std.bearing6200/
│   └── …
└── andrej.bracket-motor-mount/  # a user-authored component
    ├── component.toml
    ├── source.onecad            # frozen document (document kind)
    └── preview.webp
  • Package = directory. Each component is a self-describing folder. Sharing a component is zipping a folder; a registry is a hosted collection of the same folders behind the same manifest format.
  • Content-addressed blobs. Geometry and STEP payloads reuse the existing sha256 pattern from imports.rs — a blob is stored once and referenced by hash, deduplicated across components, and integrity-checked on read.
  • library.json is the index. It maps id → version → package path, and caches the search metadata. When a registry arrives, the index simply gains remote entries with a download-on-first-use cache — the local format never changes.
  • Identity is namespaced from day one (onecad.std.* for built-ins, <user>.* for authored) so a future registry never has to reconcile collisions.
Registry = additive

Because identity is namespaced, packages are self-describing, and blobs are content-addressed, a registry is just a remote library.json + a blob fetcher. Nothing about local placement, caching, or NeedsRepair changes. The design deliberately spends a small amount of structure now to avoid a format break later — this is the "local-first, registry-designed-in" answer the direction called for.

Integrity and trust

Every package's revision is a content hash of the whole package. A placed instance records the id + version + revision it was placed from. On open, OneCAD verifies the local package still matches the recorded revision:

  • Match → the cached geometry is authoritative; nothing to do.
  • Package missing or hash mismatch → the cached geometry still renders (the document is never broken), but the instance is flagged NeedsRepair with "component definition changed or unavailable" — the user chooses to adopt the new revision, locate the package, or detach. Never a silent swap.
  • New version available (same id, higher semver) → an opt-in "update available" affordance, per Onshape's versioned-link model. Upgrades are a user action, not an ambient event.
07

The parametric engine

The research converges on one pattern, proven by BOLTS and FreeCAD alike: separate dimension data (tables) from geometry generators (code). One row per nominal size, keyed by a canonical size string; a generator looks up the row and builds the B-rep. In OneCAD, generators are built-in and run through the existing worker op path — no new execution path, and emphatically no JavaScript on the kernel path.

The parameter roles — who is allowed to change what

From SolidWorks' Library Feature contract, the single best existing mental model for "parameters survive":

RoleMeaningExample (ISO 4762 M6×20)
freeUser-editable per placed instancethread = M6, length = 20, thread_detail = cosmetic
tableDerived from the standard's dimension table, keyed by the free size — locked to the userhead_d = 10.0, head_h = 6.0, socket = 5.0
computedPure geometry, derived by formulahex across-corners e = 2s/√3; partial-thread length b = 2d+6 (l ≤ 125)

The table key is the thread designation, not a raw diameter — an "M6 washer" has a 6.4 mm hole, so the key and the physical dimension must be different things. Length is free but constrained: snap to the ISO 888 preferred-length series and validate against the per-size minimum.

The seed catalog — what's actually in the box

Fasteners — table-driven, BOLTS-seeded

The highest-value, cleanest-licensing content. ISO 4762/DIN 912 socket cap, ISO 7380 button head, ISO 4014/4017 hex bolts, ISO 4032 nuts, ISO 7089/7093 washers — M2 through M12, the prosumer range.

  • Dimension data seeded from BOLTS (LGPL, redistributable with notice) — see the licensing reality below.

Bearings — pure lookup

Deep-groove ball bearings per ISO 15. Only three dimensions matter for placement — bore, OD, width — fully determined by the bearing code (608 = 8×22×7). No parametric geometry needed; a stepped ring suffices.

Motors — NEMA frames

NEMA 17 / 23 steppers: faceplate square, hole pattern, pilot Ø/height, shaft Ø/length are fixed; body length is a free per-instance value (it scales with torque). The four mounting dimensions are what placement needs.

The extension point

Each generator is a small, versioned module declaring its table schema and build function. Adding ISO 4026 set screws or 625 bearings is adding a table + a recipe, not a new system.

Threads — cosmetic by default, helical when it counts

Mainstream CAD defaults to cosmetic threads for measured reasons: a true helical sweep is one of the most expensive features in a kernel (~7s vs ~0s per part in SolidWorks benchmarks, 60k+ triangles vs ~0), and machined threads are manufactured from the callout, not the solid. OneCAD should ship three detail levels, settable per instance via the thread_detail parameter:

  • Cosmetic (default) — a cylinder at pitch diameter plus the designation metadata. Assembly-safe, fast, and the BOM still reads "ISO 4762 M6×20."
  • Simplified — annular grooves at the pitch, for visual weight without the sweep cost.
  • Modeled — true helical ISO 68-1 profile, reserved for 3D-print-ready output. Opt-in, per instance, never the default.
The licensing reality — what can actually ship in the box

This is where the research gets blunt. McMaster-Carr, GrabCAD, Misumi, SKF, and 3D ContentCentral all prohibit bundling — their models are "design-in only," no redistribution, and McMaster litigates to protect its catalog data. The one mature, legally bundleable dataset is BOLTS (~80 part classes, ISO/DIN/EN/ASME, LGPL 2.1+ with per-part license tracking) — fasteners-heavy and semi-dormant, but the dimension tables are exactly the seed the generator needs. FreeCAD's Fasteners tables are richer but GPLv2 today (an LGPL relicense is endorsed but unfinished). For everything beyond fasteners — bearings, motors, vendor-specific parts — the honest paths are table-driven models OneCAD authors itself (bearings, NEMA motors) and, later, a TraceParts API partnership (the one channel explicitly built for third-party CAD apps, with attribution) or user-credentialed McMaster API access. The built-in box ships clean: BOLTS-seeded fasteners + self-authored bearing/motor tables. No scraped content, ever.

08

Authoring — "Save as Component"

The market gap the research kept surfacing: every system is either closed-polished or open-janky, and Onshape users' #1 request is their own parts with the built-in UX. OneCAD's answer: a user captures any body or selection as a first-class component that lives in the same panel, searches the same way, and snaps with the same placement machinery as built-in content.

The capture flow

  1. Select and invoke. Right-click a body (or a history subtree) → Save as Component.
  2. Declare the parameters. OneCAD lists the driving dimensions of the selection; the author assigns each a role — free (user can change at placement), table-like locked, or placement — the SolidWorks Locating/Internal/Size split, applied to whole parts.
  3. Place attachments. The author clicks faces/edges to define mate points ("this face seats," "this is the shaft axis"). OneCAD stores them as local frames on named geometry. This is the 60 seconds of work that makes the component snap forever after.
  4. Name, categorize, thumbnail. A viewport snapshot becomes the preview; the author sets id (andrej.motor-mount), category, and tags.
  5. Save. The document is frozen and written as a source.onecad package. It appears in the panel immediately, indistinguishable from built-ins except a "mine" badge.
Why parameters survive here when they don't in Fusion

Fusion's pain — consumers can't drive a linked component's parameters per-instance — comes from its parameters living in a foreign file. A OneCAD document-kind component replays its own history with the instance's parameter overrides, so parameterization is total by construction, like Onshape's FeatureScript but without asking the author to write code. The author captures a model; the parameter roles decide what stays adjustable.

Authoring guardrails

  • Validation at save, not at first use. A component with no attachments gets a gentle prompt ("add a mate point so it snaps into place"), not a hard error. A component whose parameters don't drive the geometry fails validation with a specific reason.
  • The solid-only constraint is honored. OneCAD's publication policy is solid-like (single-solid at the top level, single_solid_policy in ShapeAudit.cpp). A multi-body capture is offered a choice: union into one solid, pick the primary body, or save as separate components. This constraint is stated honestly rather than discovered by the user at placement time.
  • Versioning is automatic. Re-saving a component bumps its semver; existing placed instances keep their recorded revision and offer opt-in upgrade — never an ambient change.
09

Project templates

Templates are the same idea as components, one level up: a frozen .onecad document offered as a starting point. The SolidWorks model is the proven one — a template is just a document that can contain starting geometry, units, and settings, offered in a picker at New.

The repo makes this nearly free: the start screen already has a ProjectCard / RecentGrid anatomy. Templates become a "New from template" row above the recent-projects grid — same card shape, same hover, but each card is a template. Choosing one instantiates a copy as a new untitled project; the template itself is immutable.

  • A template is stored as a package in the same library root (templates/ instead of a component folder), so the same storage, integrity, and future-registry mechanics apply.
  • Ship 3–5 honest starters: Blank, 3D-printer part (mm, XY-on-bed datum, print-oriented defaults), NEMA motor mount plate, enclosure base. Each is a real, useful starting point, not a demo.
  • "Save as Template" sits beside "Save as Component" — a user turns any project into a reusable starting point with one action.
  • Templates and components compose: a template can itself contain placed components, which resolve through the normal instance machinery.
10

The UI surface

Per ADR-0003, this is a slot contribution, not raw DOM — the host owns the panel frame, resizing, focus, and theme; the library owns only its content. This is also where the library pays down two debts the platform refactor left behind.

The Library panel

Placement & structure

A shell.left contribution, sibling to the tree. Top: a search field with filter chips (category, standard, "mine"). Body: a category tree (Fasteners → Socket Head → ISO 4762) with a card grid of thumbnails. Each card shows name, designation preview, and a source badge (parametric static mine).

Insert interaction

Drag onto the viewport → the placement gesture from §05 (ghost, snap preview, flip, auto-size). Double-click → place at origin with the parameter popover open. Selecting a card opens a small configurator: the free parameters as a compact dropdown set, a live 3D preview, and the resulting designation string updating in real time.

Two platform debts, paid

  • The background-tasks chip finally gets a producer. Indexing the library, importing a package, and generating a modeled-thread preview are exactly the begin/setProgress/end work the chip was built for and currently has no caller for. The library is its first honest job.
  • The instance is a first-class history node. Consistent with the modeling UX audit's demand that Pattern/Mirror/Boolean publish as uniquely-named editable history nodes — a placed component appears in history as "ISO 4762 M6×20" with its parameters and output lineage, editable like any other operation. No inert, invisible insertions.
Consistency with the modeling contract

The whole flow obeys the OneCAD Modeling Contract the UX audit called for — Awaiting input (dragging, no target) → Live result (ghost + snap preview) → Valid/invalid (snap target found / not) → Commit (click) → Discard (Esc). Numeric entry in the configurator follows the same routing rules as every other tool: type to the primary value, every keystroke previews, Enter applies, blur never required. The library should be the first feature built natively on the contract, not another exception to it.

11

Phasing — how to build it without boiling the ocean

The ambition (static + parametric, mate-like placement, authoring, templates) is large, so sequencing is everything. The rule: each phase ships something usable, and no phase's work is thrown away by a later one.

P0Foundation spike — pick & classifyde-risk first
  • Prove the interactive surface classification (plane / cylinder / circular edge) on a hovered pick, read-only, fast enough for live preview.
  • Prove a generator kind end-to-end with one hard-coded fastener (ISO 4762, M6 only) through the worker op path.
  • Outcome is a go/no-go on the placement UX, not a feature.
P1Static library + place-at-targetfirst shippable value
  • Library root + component.toml + library.json index; Embedded (STEP) source kind only.
  • PlaceComponent + DetachComponent; cached geometry; revision verification → NeedsRepair on mismatch.
  • shell.left panel with search + drag-to-place; concentric/flush snap on hover; flip key. Auto-size on holes.
  • Background-tasks chip wired to indexing. Seed with self-authored static bearings + NEMA motors.
P2Parametric fastenersthe differentiator
  • Generator source kind, general; table/generator split; BOLTS-seeded ISO fastener tables (4762, 7380, 4014/4017, 4032, 7089/7093).
  • SetComponentParams — edit a placed instance's size/length. Parameter roles enforced in the configurator.
  • Three-level thread detail, cosmetic default. Auto-size now sets the free size parameter.
P3Authoring + templatesthe market gap
  • Document source kind; "Save as Component" with parameter-role declaration and attachment placement.
  • "Save as Template" + the start-screen "New from template" row on the ProjectCard anatomy; ship 3–5 starters.
  • ReplaceComponent; opt-in version upgrade on placed instances.
P4Persistent mates + registryv2, separable
  • A mate solver over the recorded attachment pairs — moving a plate re-seats its screws.
  • The community registry as a remote library.json + blob fetcher; publish/share flows; TraceParts partnership exploration.
12

Open questions, with recommendations

The decisions above are the ones the brainstorm resolves. These are the ones it surfaces — each with a recommendation so the next conversation starts from a position, not a blank page.

Does PlaceComponent belong in KnownOperation, or is it a higher-level "placement" construct?

ADR-0002 keeps KnownOperation a closed typed enum — a new variant is a built-in change. The alternative is modeling placement as a composition of existing ops (import + transform) with library metadata attached, avoiding a new variant but weakening identity.

→ Recommend a real KnownOperation family. Identity is the whole point; a composition of generic ops would make "is this body a library component?" an inference instead of a fact — the same mistake copy-in makes, one layer down.

How do placed instances interact with the single-solid publication policy?

Today the audit enforces a solid-like top level. A placed component is one solid, so it's compatible — but a future "placed subassembly" (a motor with its connector) is a compound. Does the policy grow a tier, or do compounds stay out of scope?

→ Recommend keeping v1 strictly single-solid. Multi-body content is authored as separate components or unioned. Revisit only when persistent mates (P4) exist to give a compound meaning.

Who authors the built-in generator tables, and how are they verified?

BOLTS seeds the data, but its tables need auditing before they drive geometry. Wrong dimensions in a standard part are worse than no part.

→ Recommend treating each table as a reviewed data file with a spot-check harness (assert dk, k, s against a reference source per size), and generating kernelbench-style robustness cases from the table extremes — the harness already exists and this is exactly its job.

Does the registry wait for traction, or is the format commitment made now?

The design makes the registry additive, but committing to a stable package/manifest format is itself a constraint on future freedom.

→ Recommend committing to the format now (it's cheap and enables sharing-by-folder immediately) but not building any hosted registry until there's a user base to put in it. The format is the promise; the service is the later bet.

Is interactive face classification fast enough for live snap preview?

The single real technical risk in the placement UX — the reason P0 exists.

→ Recommend the P0 spike answer this with a number before any placement UI is built. If classification is too slow on hover, the fallback is click-to-classify-then-preview, which is slightly heavier but still far ahead of Fusion's drop-and-joint.
