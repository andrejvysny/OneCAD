Senior UX review · 2026-08-11 · Exercises 1–3

Promising direct modeling, fragmented interaction rules.

OneCAD already contains several ideas that make Shapr3D feel fast: sketch-on-face, in-canvas controls, live results, drag-direction fillet/chamfer switching, and history-based editing. The core UX problem is not a lack of good ideas. It is that each tool behaves like its own small product.

Executive verdict

Do not redesign the whole interface. First define one modeling interaction contract and migrate every operation to it. The highest-impact gains are predictable keyboard input, a screen-space gizmo layer, explicit operand roles, stable body/history semantics, and repair UI that appears only when history genuinely breaks.

Submitted evidence

What the captures show

Representative frames from the MacBook full-window session. The visual design is restrained; the interaction state is where the ambiguity accumulates.

Strong: the plane-selection task is explicit and orthographic alignment follows naturally. Issue: the inspector simultaneously reports “Under-constrained · DOF 0,” a contradictory state before geometry exists.
Trust break: the rectangle has 60 × 40 dimensions and begins on the origin, yet reports DOF 2. If the origin snap was accepted, a coincident constraint should exist and be visible; if it was not accepted, the snap feedback was insufficient.
Good primitive, weak layering: typed distance and direct drag are colocated. The blue arrow sits on a blue body and intersects the floating chip. It behaves like geometry when it should behave like screen-space UI.
Cross-tool inconsistency: Fillet/Chamfer uses the same tiny arrow/chip system; Shell has no arrow at all. The selected-edge highlight is clear, but the primary control is visually lost.
Wrong failure class: freshly selected edges enter NeedsRepair at first Apply. Repair is a history recovery concept, not normal authoring validation. The candidate list is useful, but should not be needed here.
Fast but under-specified: count, axis, and angle are compact and live. The real missing input is not necessarily radius—mainstream CAD derives radius from seed-to-axis distance—but explicit center/axis selection and seed-count semantics.
Capability bottleneck: the UI offers XY/XZ/YZ only. Everyday mirror workflows need a planar face, datum plane, or construction plane as the reference.
Publication ambiguity: patterned outputs become bodies with duplicated names and no visible generating feature. The user cannot tell whether instances are linked, merged, copied, or editable later.

Move tool comparison

OneCAD (current): the horizontal options chip crosses the gizmo center, hiding the pivot, axis stems, and handle intersections. Three large full-circle rotation rings overlap one another and compete with translation arrows. Move/Rotate and X/Y/Z modes live in the chip, separating axis meaning from the spatial handle.
Shapr3D reference: the pivot stays clear. Translation arrows, planar handles, and compact curved rotation handles form one small spatial widget. Angle and Copy controls sit beside—not across—the widget. Borrow the hierarchy and separation, not the exact styling.
Priority findings

The nine issues to fix first

Ranked by modeling speed, predictability, and risk of users believing the wrong geometry/history state.

P0
01

One tool contract, not thirteen micro-interactions

Extrude auto-focus differs from sketch dimensions; distance may update only on blur while count updates live; Shell omits the manipulation arrow; Combine can appear inert until another click. These are not separate bugs—they reveal the absence of a common operation state model.

  • Every operation must expose the same states: Awaiting input → Preview valid/invalid → Applied or discarded.
  • Every dimension-bearing operation gets the same input routing, keyboard rules, Apply/Discard placement, and accessibility.
P0
02

Make gizmos screen-space controls—including Move

Blue-on-blue and red-on-red arrows disappear, collide with geometry, and overlap chips. Move is the clearest failure: the options row passes through the pivot while three large rotation circles obscure one another and the translation axes. Render handles in a dedicated overlay layer with adaptive contrast, fixed-pixel hit areas, depth-independent visibility, and collision-aware chip placement.

  • Keep the Move pivot unobstructed; place the options chip outside the gizmo bounding box with a leader, or dock it to a viewport-safe edge.
  • Replace full-size rotation circles with compact, curved double-headed rotation handles near the pivot; keep axis identity through color and orientation, and enlarge only the hovered/active handle.
  • Keep translation arrows visually primary, planar handles secondary, and rotation arcs tertiary until hovered.
  • Put X/Y/Z identity on the corresponding handle; do not make chip tabs the only axis cue.
P0
03

Standardize numeric entry: type, preview, commit

When a tool has one obvious primary value, typing must route there without clicking. Every keystroke updates preview; Enter applies the operation; Tab cycles secondary fields; Escape backs out predictably. Never require blur to update geometry.

P0
04

Define body-result semantics before polishing Pattern

Linear/Circular Pattern appears to duplicate the seed into a new result while retaining the source, producing overlap. Mirror produces separate bodies. Combine-Cut was not visible as a history feature. Choose explicit modes and communicate them before Apply.

  • Body pattern / New bodies: source stays; create count−1 additional bodies. Never duplicate the seed position.
  • Feature pattern / Merge: one editable history feature modifies the owning body.
  • Mirror: New body or Merge result; source remains exactly once.
P0
05

History must publish every committed modeling operation

If Pattern, Mirror, or Combine is committed, it must appear as an editable feature with unique naming, operands, parameters, and output lineage. Flattening to anonymous bodies destroys the promise of history-based CAD.

P1
06

Separate authoring validation from NeedsRepair

A new Chamfer that cannot bind selected edges should remain in-tool and ask for reselection. NeedsRepair is reserved for a previously valid history node broken by upstream edits. The current repair panel also says “5 candidates” then sometimes “No candidates,” which is internally contradictory.

P1
07

Make Boolean roles explicit

Combine should never look inert. Show Target and Tool(s), identify them in the viewport and chip, allow swap, expose Keep tools, and preview semantic volumes: survives, removed, and intersection. Plasticity’s explicit target/tool/Keep Tools vocabulary is the useful benchmark here.

P1
08

Fix sketch constraint truth before adding more automation

“Under-constrained · DOF 0” is impossible copy. Starting at the origin should create a visible coincident constraint only when the snap is actually accepted. Do not silently infer; show the snap glyph and persist the relation. With width and height applied, the rectangle should then become Fully constrained.

P2
09

Broaden references, not panels

Mirror should accept planar faces and datums. Patterns should pick arbitrary axes/edges/construction axes. Circular Pattern does not inherently need a radius field—the seed-to-axis distance defines it—but it does need an explicit, editable axis/center reference and clear “total instances” wording.

Proposed interaction language

The OneCAD Modeling Contract

A compact system that preserves the current in-canvas character while making every tool predictable.

STATE 1Preselection: hover and select valid geometry before invoking a tool.
STATE 2Awaiting input: tool says exactly what is missing; valid pick classes highlight.
STATE 3Live result: real uncommitted geometry, clearly marked as preview.
STATE 4Valid / invalid: Apply enables only for a publishable result; reason is inline.
STATE 5Commit: one history node appears; outputs and source visibility follow explicit mode.

1. Selection vocabulary

Foundation
  1. Hover: light accent outline, no persistent fill.
  2. Selected: stronger accent outline + restrained fill.
  3. Operand roles: labeled badges in chip and viewport—not color alone.
  4. Invalid reference: error outline and reason at the cursor/chip.
  5. Selection filter is tool-owned and visible: Face, Edge, Body, Axis, Plane.

2. Gizmo + chip

Immediate
  1. Render above geometry with fixed pixel size and a contrasting halo.
  2. Anchor to geometry via a leader line, but avoid model and chip collisions.
  3. Chip follows the relevant handle, constrained to viewport safe areas.
  4. Primary value, mode, Apply, and Discard are always in the compact row.
  5. Expanded options never replace or move the primary row.

3. Keyboard contract

Immediate
  1. Start typing → primary numeric parameter, no click required.
  2. Every valid keystroke → live preview.
  3. Tab / Shift-Tab → next/previous parameter.
  4. Enter → Apply when valid; Escape → discard current edit, then exit tool.
  5. Mouse blur never becomes the only way to update a value.

4. Result semantics

Trust
  1. Before Apply, summarize: “3 total instances · 2 new bodies · source retained.”
  2. New Body, Add/Merge, Cut, Intersect are explicit and persist in history.
  3. Pattern count always means total instances and includes the seed.
  4. Source exists exactly once; generated output never overlaps it invisibly.
  5. Unique names are minted deterministically and visible immediately.

5. Error + repair

Correctness
  1. Pre-commit failure remains in the active tool with selected references intact.
  2. Post-edit broken references become NeedsRepair and stop the timeline.
  3. Explain human meaning first: “Fillet lost its two source edges.”
  4. Show candidates in context; hover candidate → viewport highlight.
  5. Never claim candidates exist if none are selectable.

6. History publication

Parametric CAD
  1. Every commit creates one editable operation node.
  2. Node summary carries meaningful parameters: “Circular Pattern · 3 × 120° · Z.”
  3. Generated bodies nest under or link to the operation.
  4. Double-click reopens the same in-canvas chip and preview.
  5. Failure, suppression, and repair states are visible in both tree and viewport.

Implementation sequence

Correctness-first UX roadmap

Sequence shared primitives before individual tools. Otherwise each operation will keep re-implementing and drifting from the same behavior.

Phase 0
1–2 weeks

Freeze the interaction contract + red repros

Write executable behavior contracts for input routing, blur, preview, Apply/Discard, gizmo visibility, result summary, history publication, and authoring-time reference failure.

DOF 0 contradictionExtrude type-to-enterDistance live updateFresh chamfer repairPattern seed overlap
Phase 1
2–4 weeks

Build shared front-end primitives

One OperationHUD, NumericRouter, GizmoOverlay, SelectionPrompt, OperandSummary, ValidationMessage, and collision-aware placement system. Migrate Extrude and Fillet/Chamfer first because they define the desired feel.

Phase 2
3–5 weeks

Migrate operation tools

Shell, Hole, Offset Face, Draft, Boolean, Linear/Circular Pattern, and Mirror adopt the same state machine and input rules. No operation-specific focus or blur behavior remains.

Phase 3
4–6 weeks

Fix body and history semantics

Define source retention, total-instance count, output body modes, merge behavior, unique naming, and first-class operation nodes across Rust, protocol, and worker. Pattern/Mirror e2e coverage becomes mandatory.

Phase 4
2–4 weeks

Repair that users can trust

Separate pre-commit invalid selection from post-edit NeedsRepair; add viewport-linked candidates, human-first copy, deterministic reselect flow, and no-candidate truthfulness.

Definition of done

What “Shapr3D-level” means for OneCAD

Fast without guessing

A user can preselect geometry, invoke a tool, type a value immediately, and press Enter. The model, chip, and history all agree on what will be created.

Consistent without being generic

Tools share state, keyboard, preview, and commit rules while retaining operation-specific controls where geometry genuinely differs.

Parametric without ceremony

Every operation is editable later, every output has clear lineage, and direct manipulation updates the same history node rather than hiding a second model.

Correctness visible in the UX

Invalid authoring is stopped before commit; broken history is explained and repairable; silent overlap, missing features, and ambiguous bodies are impossible.
